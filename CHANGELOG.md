# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The faults that make invalid messages, the exits of the node shim and every refusal of the link of the panel are tried:** the oversized-targets fault on a fixed stream (every Nth reading, zero count, only readings), all the faults repeatable, the shim command for a good run, a driver that fails, the wrong number of readings and a problem found by the check of the node, and the link of the panel to the broker with a stand-in for the broker library (library missing, address that is not a broker, unreachable, silent, refused-free good run, a damaged command ignored). Sixteen tests, no socket and no program started.
- **The run of the bench and the corners of the command line are tried with stand-ins:** the bench is run end to end with the server, the broker and the node programs replaced (the environment given to the server, the check each road adds, a server that does not start, a missing client library, a child that has to be killed), and the command line is tried on an interrupted run, the driver of a server, the check of the sync of a panel, an error of the broker and a message that travels only over the broker. Coverage of `bench_ci.py` goes from 50% to 98% and of `cli.py` from 85% to 98%.

- **The publisher on a broker is tried with a stand-in for the client:** a broker that accepts (credentials, sorted compact messages, the count), one that refuses, one that does not answer, one that cannot be reached, a publish that is not taken or refused, publishing before opening, a missing client library and every check of the address of the broker.
- **The battery-writing loop is tried in its parts that need no server or broker:** the fake console, the node that answers arm, execute and cancel (disabled by default, wrong serial, one arm and one execute, an execute for another order, a made-up token), the administrator that signs in and proves themselves again against a server on the loopback, and the wait for a condition.
- **Vision scenarios in files:** `--vision-scenario FILE` plays a JSON file (schema `armor-vision-scenario/1`, documented in `docs/VISION_SCENARIOS.md`) with cameras, their detection zones and their mode profiles (the shape the server hands to the observation service) and a timeline of the arming mode and of objects walking across the picture, and prints the vision events the rules would raise (`armor.vision.event/v1`, one per line, in the contract of the shared vision event). `--check-vision-scenario` validates the file and `--verify-vision` compares the events with the `expect` and `forbidden` rows of the file. A mode with no profile watches every zone. It is a twin of the rules, not of a detector. Two examples in `examples/vision`. Tests: 22 more.

- **A floor for the test coverage:** the workflow `coverage-floor.yml` runs the Python tests under coverage and fails when the lines or the branches fall below `docs/coverage_threshold.json`. Floor of src/armor_simulator: lines 85.5, branches 85.5 (measured 86.21 and 86.32). Raising it is a change of that file, made with a figure measured by the workflow.

- **Tests for the helpers of the bench without Docker:** the two HTTP readers, the waiting loop, the list of checks, the report the command writes, the options that reach the run and the camera checks seen from a stand-in server (one that refuses everything and one that answers as a good one does) are tested on the loopback address, without a server, a broker or a camera.

- **A fake pan-tilt head:** a camera of the file may say `"ptz": true` and then answers the move command of a Hi3510 unit (`/cgi-bin/hi3510/ptzctrl.cgi?-act=left`) with `[Succeed]set ok.` after its login, refuses a wrong login or an action that is not in the table, and keeps the list of the moves it was told. The server bench uses it: the real server finds the head with the login it stores, moves it, stops it by itself, refuses a command that is not in the table, tells a refused login and does not move a camera that has no credentials.

- **The battery-writing loop:** `python -m armor_simulator.bench_ci --battery-loop` starts the real server with `ARMOR_BATTERY_WRITE=1` and runs a simulated gateway node on the broker (`battery_loop.py`) that keeps a FAKE Pylontech console; the node's own switch is off until the bench turns it on. An administrator who has proved themselves again arms an output change, a wrong serial is refused (by the node when arming, by the server when executing), the right one executes and the console changes, the server keeps the difference and offers the restore, which is armed and executed, and an armed order that is withdrawn is never executed. Evidence is the simulator: nothing is written to any battery.

- **The HMI node in the MQTT shim:** `--node hmi` plays the health reports of a wall panel, with a sag of the supply (restart with the reason brownout, the uptime starting again, a last error) into `tests/mqtt_shim.cpp` of ARMOR-NODE-HMI, which writes them with the firmware's own report code; the shim refuses a run that does not show the restart, and the server bench checks that the real server lists the panel as an HMI with the brownout (`--shim-hmi-driver`).

- **The alarm node in the MQTT shim:** `--node alarm` plays the steps of a wired panel (arming away, a door loop that opens, a power cut and the restart that takes the alarm back, the PIN that disarms, arming again) into `tests/mqtt_shim.cpp` of ARMOR-NODE-ALARM, which runs the real zone classifier, panel and message writer; the shim refuses a run in which the panel did not report every phase, and the server bench checks that the real server shows the node armed in away mode (`--shim-alarm-driver`).

- **The solar node in the MQTT shim:** `--node solar` plays the replies of a simulated inverter (text framed by the node's own code) and the console tables of a Pylontech stack, with one round on the battery after a mains loss, into `tests/mqtt_shim.cpp` of ARMOR-NODE-SOLAR; the server bench checks that the real server lists both devices in its solar readings (`--shim-solar-driver`).

- **The MQTT shim, node by node:** `python -m armor_simulator.node_shim --driver PROGRAM --node-id ID --mqtt-url URL` plays the serial stream of the radar modules into `tests/mqtt_shim.cpp` of ARMOR-NODE-RADAR (the real framer, decoder, track builder and message writers of the firmware, built for a computer) and publishes what it prints on a broker with the topics, the payloads and the QoS of the real node. The server bench runs it when it is given `--shim-driver` and a broker, and checks that the node shows in the status of the server. It proves the message code of the node against the real server; the radio, the clock and the broker client of the board are still the board's. The electrical node has its own (`--node electrical`: the Modbus replies of the meter bus into the real PZEM decoder and message writer of ARMOR-NODE-ELECTRICAL; the server bench checks that its meters show in the readings of the server). Tests: 9 more.
- **The server bench plays fake IP cameras too:** two cameras on the loopback (a walker, and one that answers an error on purpose) are configured in the built server through its own route; the preview of the first reaches the console through a ticket as a real PNG, the second is a clean refusal and the server goes on. It proves the code path of the picture, not any real camera.

- **A recording of the HTTP reports is played in the bench too:** `examples/recordings/http_routes.jsonl` holds the report of an alarm panel, a meter, a solar inverter and battery and a network node as a server copies them, and one alarm report the server refused (the siren sounding outside the alarm phase); the bench plays it twice against the real server, once with the refused one left out (the panel and the meter show) and once with it (refused again for the same reason). Tests: 2 more.
- **The buses of the field nodes, played into the real firmware code:** `python -m armor_simulator.node_bench --bus ld2450|pzem|pylontech|alarm-loop|hmi-feed --driver PROGRAM` generates the traffic of one bus (the serial stream of the LD2450 radar modules, the Modbus replies of the PZEM meters, the console of a Pylontech stack, the voltage of a wired alarm loop, the live channel of the panel), spoils it on purpose (noise, cut or garbled frames, flipped bits, exceptions, silence, impossible values, bounce, a cut or shorted wire, oversize frames) and compares what the driver answers with what it must answer. The drivers (`tests/sim_bench.cpp` in each node repository) are built from the core files of the firmware, with no board and no ESP-IDF. `--record` and `--replay` keep and repeat a set of cases (`docs/NODE_BENCH.md`).
- **The virtual bench without Docker:** `python -m armor_simulator.bench_ci --server-dir ../ARMOR-SERVER` starts a built server on a free loopback port, feeds it over HTTP (and through a Mosquitto broker when one is installed), refuses impossible readings, survives a message sent twice and a slow link, and plays a recording of the traffic of a server (`examples/recordings/incident.jsonl`) again, checking the status of the server at each step. The workflow `Simulation bench` runs it on every push and once a week.

The format stays one `topic` and `payload` per line, so every earlier recording still plays.

- **The launchers find the shared repository through `ARMOR_COMMON_DIR`:** `build`, `build-test`, `test` and `run` (`.sh` and `.bat`) use the folder named by that variable when it is set and the sibling `ARMOR-COMMON` folder otherwise, so a checkout with another layout builds without changing a file.

## [0.3.4] - A virtual bench for Docker, the serial line of the energy meters, the other node types, an MQTT output, several nodes at once and people walking across them

- **Walks along a polyline in an alarm scenario:** the new `walk` event moves one or more people along 2 to 32 points of a node at a set speed (the radial speed of each track is worked out from the positions), with `examples/alarm/walk-across-two-nodes.json`.
- **Several nodes at once:** `--nodes north-1,south-1` simulates up to eight radar nodes and the scenario `relay` hands one walker from node to node.
- **The other nodes:** `--info` (what a node says about itself), `--alarm-node ID` (a simulated alarm panel that arms, counts down, sounds and disarms) and `--network-node ID` (a simulated network watcher whose devices come and go); the alarm and network messages are also delivered to `/api/v1/alarm/state` and `/api/v1/network/state`, and `--validate` checks them.
- **Publishing on an MQTT broker:** `--mqtt-url` (with `--mqtt-user`, `--mqtt-password-file`, `--mqtt-allow-network`) also publishes every message with its topic, so the MQTT road of the server can be exercised; the broker must be on this machine or a private network unless allowed, and `paho-mqtt` is an optional extra.
- **Parity with the conformance vectors:** tests compare the fields and types of the telemetry, health, info, alarm and network messages with the vectors of ARMOR-COMMON, and the contract accepts all of them. With `ARMOR_FIRMWARE_SAMPLES` naming the output of the radar firmware's `emit_samples` (built on the host), the same comparison is made with what the real serialiser prints; a tiny broker on the loopback checks the publishing with the real `paho-mqtt` client.
- **The battery stack reuses the reading of the inverter** of the same sample instead of working it out twice.
- **A virtual bench: simulated nodes delivering to the server in real time, from a container:** the `Dockerfile` of the simulator and `docker/bench.sh` run 1 to 8 nodes (`bench-1`...) side by side, round after round, with the scenario, the light, the interval, the solar and electrical messages and a repeatable fault chosen by `ARMOR_SIM_*` variables; the ingest token comes from the environment or a file and is never on a command line, a failed round (the server restarting) is retried, and `ARMOR_SIM_DRY_RUN=1` prints the commands. Tests: 5 in `tests/test_bench_script.py` (the commands are parsed by the real command line, the refusals, a round delivered to a local server).
- **The serial line of the energy meters, over TCP:** `--meter-bus-port PORT` (with `--meter-bus-config`, `--meter-bus-host`, `--meter-bus-allow-network`, `--meter-bus-seconds`) answers Modbus-RTU requests like a PZEM-004T v3 (AC) and a PZEM-017 (DC) answer them, with the readings of `--electrical`, so the code that reads the meters can be tried without one. It is read only (the writes and the reset of the energy counter are refused and counted), a frame with a bad CRC gets no answer, and the meters, their thresholds and the faults (a silent meter, a garbled reply, an exception) live in a JSON file (`docs/METER_BUS.md`). It listens on the loopback unless told otherwise. Without the new options the output is the same, byte for byte. Tests: 210 (before 182).

## [0.3.3] - A run can be recorded and played again and the delivery to a server can be spoiled with latency, drops or duplicates

- **A run can be recorded and played again:** `--record FILE` also writes every emitted message to a JSON-lines file (an existing file is never overwritten) and `--replay FILE` emits the messages of such a file instead of generating them; faults, `--validate` and delivery to a server still apply to a replay. A recording that has a bad line, a value that is not JSON (NaN, Infinity), a topic outside `armor/` or more than 64 MiB is refused whole. Without the new options the output is the same, byte for byte.
- **The delivery to a server can be spoiled, not only the messages:** `--http-fault latency|drop|duplicate` (with `--http-fault-every`, `--http-latency-ms`) makes every Nth message arrive late, never be sent or be sent twice, to test how the server and its clients cope with a bad link; it needs `--server-url` and is off by default, and the end of the run says how many messages were affected.
- Tests: 182 (before 174).

## [0.3.2] - The panel sync is checked in the CI against a real server and a real broker

- **The panel sync is checked in the CI against a real server and a real broker.** `panel-sync.yml` (a workflow of its own, off with the variable `ARMOR_PANEL_SYNC=off`) installs Mosquitto, builds the ARMOR-SERVER of the main branch and runs `tools/ci_panel_sync.py`: the simulated panel answers each command (accepts, refuses, stays silent) and `--verify-panel-sync --verify-panel-map` compares the report of the server for every mode and for the choices of the owner with what must be true. The script starts and stops both programs on loopback ports and deletes its folder; it is tested for what it does without them.

## [0.3.1] - A check of how the arming modes reach the panels, against a real server

## [0.3.0] - A simulated panel and a check of the panel sync and of its alarm against a real server

- **The panel sync check also looks at the alarm centre:** after each step it asks the server for its alarms and requires exactly one open alarm `mode_panel_sync_failed` (high, not silent) when the panel refused or stayed silent, and none when it accepted.
- **A simulated alarm panel and a check of the panel sync of a real server:** `--verify-panel-sync` connects a simulated ARMOR-NODE-ALARM panel to the broker of the server (`--mqtt-url`) and, for each behaviour of the panel (accepts, refuses, never answers) and each mode (away, home, night), chooses the mode through Studio's own routes and compares the report of the server (`panel_sync`) with what must be true: the server defends the mode whatever the panel does, the panel is asked for the profile of the mode (away, stay, night) and for nothing else, and the report says confirmed only when the panel accepted. The panel model, the check and a model of the server that is broken on purpose in several ways are covered by `tests/test_panel_sim.py`.

## [0.2.9] - Alarm scenarios checked against a real server, with the arming modes and expectations that name a zone

- **Expectations that name a zone can be checked against a real server:** the alarm of the server for a radar track names the node and not the zone, so with `--drive-server` an expectation with `zone` is now checked at the node that sees that zone (the log says so) instead of never matching; a scenario that expects an alarm in one zone and forbids it in another zone of the same node in overlapping seconds is refused with exit 2, because the server cannot tell them apart.
- **The scenarios with modes are checked against a real server:** `--drive-server` plays an alarm scenario against an ARMOR-SERVER that has the arming modes on: the `mode` events (and the changes of the calendar) become orders to `POST /api/v1/mode`, the telemetry goes to the ingest routes in real time, and the alarms the server raised are compared with the expectation of the file. A scenario can say what home and night defend in a real server (`server_modes`) and, with `--apply-modes`, the simulator defines it there; the account's password comes only from the environment or a file, and a PIN for a change that defends less is given the same way. A forbidden alarm can now name a node. A ninth example, `arming-modes-server.json`, was played against the real server and held. A scenario file played without `--drive-server` behaves as before.

## [0.2.8] - Alarm scenarios in files with their expected answers and realistic solar and electrical data

- **Alarm scenarios in files:** `--alarm-scenario FILE` plays a JSON file (schema `armor-alarm-scenario/1`, documented in `docs/ALARM_SCENARIOS.md`) with a timeline of events: people who cross several zones one after another, a pet, wind, a sensor that is stuck, noisy, drifting or dead, a node that loses its link, a mains outage and the mode of the system, also by the calendar (home, away, night). The file may say what the system is expected to answer (which alarms, in which order, in which window of time, which ones must not happen); `--verify-alarms` compares the alarms a server raised with it and exits 1 when they differ, so the files serve as test cases for the server. `--check-alarm-scenario` only validates. The reading is strict and refuses the whole file at the first thing that is not understood. Eight examples are in `examples/alarm/`.
- **Realistic solar and electrical data:** `--energy` (with `--energy-config`, `--energy-days`, `--energy-step-s`) emits an inverter, a battery stack and an electrical node from a real-time model: a sun with clouds, a house that eats by the hour, a tariff, a Pylontech-style battery with cycles and a meter with noise and holes. Deterministic for a seed; every setting lives in a JSON file (`docs/ENERGY_MODEL.md`). Tests check that there is no production at night, the state of charge stays between its limits, the energy balances at every step and the counters never go down.
- Both are opt-in: without the new options the output is byte for byte what it was. Tests: 127 (before 63).

## [0.2.7] - The lights of Project status follow the evidence of the manifest and the pictures of the README from shared tools

- **The lights of Project status follow the evidence of the manifest:** the manifest says how far the repository has been shown to work (`evidence`: `host-test`, `simulator`, `bench` or `field`) and the validator fails when a light is above what that evidence and the maturity allow (`tools/status_lights.py`), so a green that never ran on real hardware cannot come back.
- **The layout of the README is checked in the CI:** the validator runs the shared `tools/universal_readme_check.py` and fails when the README differs from the universal layout.
- **The pictures of the README come from shared tools:** `tools/make_architecture.py` draws `images/architecture.svg` from `docs/architecture.json` and `tools/make_structure.py` draws the Repository Structure (the text tree and the animated picture) from `docs/structure.json`; both measure every text, and `--check` fails when a picture, its description or the code it points to disagree. They are vendored from ARMOR-COMMON like the shared CI checks.

## [0.2.6] - A node of 270 degrees and `--fault-topic`

- **A node of 270 degrees:** the three sensors face -75, 0 and +75 degrees (neighbours overlap by 45 degrees; only the 90 degrees behind the node are blind), like the radar node, instead of a 90 degree corner. `speed_mm_s` is now the radial speed seen by the sensor, negative when the object comes closer, instead of a constant per scenario.
- The repository has a security policy, a code of conduct, a contributing guide and a support file.
- The banner follows the animated style of the ecosystem banners, with the name, the kind and the technologies of the project.
- **`--fault-topic`** limits a fault to the radar node's telemetry, its health, the solar readings or the electrical node's, so one node can fall silent while the others go on talking; the count of `--fault-every` is of that kind, and a kind with nothing to spoil is refused.

## [0.2.5] - A night that is dark, dates the server believes, and tracks like the firmware sends them

- **`--light cycle` has a real night** and the same day as the solar and electrical sources (240 samples), from 0.3 lux to about 50 000 at noon; before the "night" was 4 000 lux and the sun rose ten times a day, so the day/night profile was never exercised.
- **`--start-ms`** dates the samples (`now` or a number); with the default `0` runs stay identical, but the server replaces such dates by its own clock, so `out-of-order` only means something with a real date. `--per-node-token` sends the token the strict server derives for each node; `--ingest-token-file` and `ARMOR_INGEST_TOKEN` keep the token out of the process list.
- **Tracks as the firmware sends them:** positions and speed are whole numbers, and a track keeps its id for as long as its object is in the scene (it was renumbered when another one left). The docstring says the angles are -45, 0 and +45 and that the real node is a 270 degree one.
- **One battery voltage:** the inverter and the battery stack agree (the inverter used to read up to 3 V above the sum of the cells).
- After delivering invalid messages the simulator says how many the server refused and how many it accepted; a URL with a hidden password or a fragment is refused; the 401 message names the right option; `--validate` says which message failed instead of a traceback; combinations that do nothing (`flapping` with no health messages, a fault every 0) are refused.
- Tests: 36 (before 31).

## [0.2.3]
